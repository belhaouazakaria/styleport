# Implementation map — repository audit and Phase 2 foundation

This is the file-level design contract and implementation audit. Phase 2 foundation behavior was verified on branch `feature/growth-agent-phase-02`; later-phase paths remain proposals. The verified production database baseline is PostgreSQL 18 self-hosted on the VPS.

## Runtime and conventions

`package.json`: Next.js `^16.3.5`, React `19.2.4`, TypeScript `^5`, Prisma/client `^6.19.3`, Auth.js/NextAuth `5.0.0-beta.32`, OpenAI SDK `^6.34.0`, Zod 4, Vitest 4. Node types are 20, but no Node engine is pinned. Scripts include `lint`, `typecheck`, `test`, `check`, Prisma generate/migrate/deploy, `start` (`server.js`), `start:editorial-worker` (`tsx`) and the bounded `growth:worker` command. `prebuild` and `postinstall` generate Prisma client.

`prisma/schema.prisma` uses PostgreSQL, `cuid()` IDs, uppercase enum values, `createdAt @default(now())`, `updatedAt @updatedAt`, explicit `@@index`, relation delete actions, and targeted `Json`. Migrations are timestamp-prefixed SQL directories (`prisma/migrations/2026...`). The current schema has no universal soft-delete: Translator, Category and AdPlacement use `archivedAt`; Translator also uses `isActive`; editorial drafts/jobs use status. Growth must specify deletion behavior per model. `TranslationLog` currently stores raw input/output text, IP hash and user agent; Growth attribution must not copy these.

Production uses PostgreSQL 18 self-hosted on the VPS. The SayTwist app connects locally to `127.0.0.1:5433`, database `saytwist`, as application role `saytwist_app`; Neon and other external managed databases are not part of the current production runtime path. Growth shares this existing PostgreSQL instance and database unless a later durable architecture decision changes that baseline. It must keep database load bounded: persistent scheduled jobs and bounded workers are preferred, with no aggressive always-on polling. `ecosystem.config.cjs` currently lists only the `saytwist` web process, while `docs/editorial-generation-operations.md` describes a separately deployed editorial worker; verify the actual PM2/cron state before adding any future Growth process. The deploy script preserves `public/generated`, whereas current image code defaults to `storage/generated`; verify persistent storage mount and backup before Growth uses disk assets.

## Current integrations and gaps

**Translators:** `lib/data/translators.ts` implements create/update/archive/unarchive/hard-delete, featured recalculation and share image generation. Admin routes under `app/api/admin/translators/` validate with `lib/validators.ts`; AI draft route calls `lib/translator-draft.ts`. `Translator.slug` is unique, and `lib/slug.ts` resolves conflicts. `isActive` and `archivedAt` determine availability. `isFeatured`, `featuredRank`, `featuredSource` support manual/automatic featured placement. No general translator version history exists. `TranslatorEditorialContent/List/Example/Faq` are published page content; `TranslatorEditorialDraft`, Job and JobItem persist review-only generation. Existing editorial worker uses `UPDATE ... SKIP LOCKED` style claiming, stale recovery, max attempts and pause/cancel; default poll is 300000 ms, minimum 60000 ms, and quota error stops it. Do not reuse its polling loop for Growth.

**Renderer V1 — Control:** `lib/share-images.tsx` is the exact automatic translator Pin renderer. Input is translator slug/name/subtitle/short description/source and target labels plus platform name; content hash selects deterministic palette and filename. It composes `Click Here To / Translate / Your Text to / [style phrase] / Style!`, plus brand/source-to-target footer. Next `ImageResponse` produces a 1000×1500 PNG. It tries Anton and Montserrat fonts fetched from Google Fonts GitHub/jsDelivr URLs (the `@main` source is not version-pinned) and falls back if unavailable. Output defaults to `storage/generated/pins`, served at `/generated/pins/[filename]`; `Translator.shareImagePath/hash/updatedAt` hold the current asset. `/translators/[slug]/pin-image` ensures and redirects to it; admin regenerate endpoints and featured backfill also call it. Old asset removal is best effort after reference check; force regenerate can create a new name. Known limits: fixed copy/layout, external font fetch dependency, no renderer/template/variant ID, no campaign or Pin outcome association, and local filesystem durability needs deployment verification. Growth later records renderer key `v1-control`, renderer version/hash, asset checksum/path, headline/CTA/theme, candidate/publication/experiment IDs. The separate client canvas result Pin in `translator-card.tsx` posts PNG to `/api/pinterest/result-image`, 3 MB cap; it is temporary (`storage/generated/result-pins-temp`), cleaned after six hours or >300 files, and opens Pinterest user share intent. It is **not** Renderer V1.

**Analytics:** `app/api/translate/route.ts` writes `TranslationLog` SUCCESS/FAILURE/BLOCKED including translator/model/tokens/estimated cost. Phase 4 stores Pinterest organic inventory and metrics. Phase 5 adds issued refs, hashed-token sessions, bounded first-party events, server-authoritative SUCCESS completion links, and durable daily aggregates. The translation route records attribution only after the SUCCESS log exists and isolates every attribution failure from the response. `/admin/growth/analytics` remains Pinterest-reported data; `/admin/growth/attribution` reports bounded first-party aggregates. Ideas events remain unwired until Phase 9.

**AI/settings/security:** `lib/openai.ts` uses one OpenAI client and Responses API with model fallback, a second empty-response attempt, tokens returned to callers. `lib/pricing.ts` estimates selected text models; unknown model costs return zero. No image-model integration or universal AI cost ledger. `AppSetting` is key/JSON and `lib/settings.ts` maps a fixed set with a 60-second cache. `auth.ts`/`lib/permissions.ts` use Auth.js sessions and ADMIN role, routes use `adminRouteGuard`, Zod validates input, `lib/rate-limit.ts` is in-memory (single-process only). `next.config.ts` sets CSP, referrer policy and security headers. No general token encryption utility exists. Growth OAuth credentials need new authenticated encryption and key rotation design, never reuse plain Auth.js `Account` token columns for Pinterest business connections. Admin mutation routes must validate origin/CSRF assumptions for Auth.js cookies and sensitive actions.

**SEO and tests:** Public translator page has canonical/OpenGraph metadata, breadcrumbs, structured editorial content and internal links. `app/sitemap.ts` lists static and translator URLs; `app/robots.ts` excludes admin/API and temporary images. Ideas needs own metadata/sitemap inclusion and duplicate-content controls. Vitest/jsdom tests live in `tests/`; Prisma editorial integration tests are opt-in via `RUN_EDITORIAL_DB_TESTS=1`. Growth has a separate opt-in `npm run test:growth-db` suite. It requires an explicit `GROWTH_TEST_DATABASE_URL`, makes `DATABASE_URL` match only for that process, and refuses every host/database except local `saytwist_growth_phase2_test`.

## Scheduling contract

Use a host scheduler or controlled PM2 cron invocation only after actual host capabilities are verified to enqueue due jobs and run a bounded `--once` worker, rather than continuously querying the local PostgreSQL instance. Persist a unique `(jobType, scheduleKey)` or idempotency key before work; claim due jobs with a transactional lock, lease and `runAfter`, cap concurrency and runtime, heartbeat during active work, and stop on kill switch/quota failures. Enqueue hourly analytics/reconciliation only when connected; daily analysis/report/health; event-triggered post-approval publication/content jobs; monthly account review; on-demand backfill/recovery. Stagger schedules and bound queries, connection use and concurrency; no aggressive or idle DB polling. No cron or PM2 process entry exists through Phase 2.

## Phase 2 implemented foundation

- `lib/growth/contracts.ts`: strict settings and bounded payload contracts.
- `lib/growth/settings.ts`: dedicated singleton `GrowthSettings` (`id=global`), disabled by default, `BALANCED`, batch size 5, versioned updates.
- `lib/growth/jobs.ts`: idempotent enqueue, one-statement bounded PostgreSQL batch claim using `FOR UPDATE SKIP LOCKED`, lease recovery, cancellation, bounded exponential retry and terminal failure. The unique, required idempotency key identifies one logical job for its full lifetime; reuse returns the existing row regardless of its state, so callers must namespace keys by operation/resource/version.
- `lib/growth/handlers.ts`: registry with only `FOUNDATION_NOOP`; unknown types fail visibly.
- `lib/growth/worker.ts` and `workers/growth-worker.ts`: explicit bounded invocation, maximum batch size 25, no timer or idle polling. The worker bootstrap calls Next's `loadEnvConfig` before dynamically importing any Growth module, so `npm run growth:worker` uses `.env.production.local`, `.env.local`, `.env.production` and `.env` with existing process variables retaining precedence. A stable configured worker ID upserts one heartbeat row, while each invocation gets a unique lease-owner suffix so overlapping invocations cannot complete each other's jobs.
- `lib/growth/activity.ts`: structured, append-only activity records written transactionally with state changes where possible.
- `lib/growth/admin.ts`: bounded status counts, oldest runnable job, latest worker execution and 12 recent activities.
- Admin routes use the existing ADMIN guard; Growth mutations require an Origin that exactly matches the trusted server-side `APP_BASE_URL` canonical public origin, so nginx's loopback listener cannot cause legitimate browser requests to fail. They also use strict input validation.

## Phase 7 implemented opportunity intelligence

Migration `20261006220000_growth_opportunity_intelligence` adds typed opportunity/status/evidence enums, immutable `GrowthOpportunityAnalysisRun`, stable `GrowthContentCluster`, per-run `GrowthContentClusterSnapshot`, bounded explicit `GrowthContentClusterMembership`, and `GrowthOpportunity`. The pipeline lives in `lib/growth/opportunity/*`; the registered job is `OPPORTUNITY_INTELLIGENCE_ANALYSIS`; the bounded ADMIN/same-origin surface is `/admin/growth/opportunities`. `npm run test:growth-opportunity-db` accepts only loopback database `saytwist_growth_phase7_opportunity_test`.

`opportunity_intelligence_v2`, `opportunity_scoring_v1`, and `content_clustering_v2` analyze the last 28 complete UTC days, with recent/previous seven-day comparisons and four weekly buckets. Queries cap eligible Pins at 500, Pin daily rows at 14,000, clusters/opportunities at 100, members per cluster at 100, supporting IDs at 20, evidence at 48 KiB, and admin rows at 50. Reaching the Pin cap marks evidence `PARTIAL`. Lexical clustering is stable and order independent, removes generic boilerplate, maps canonical `/translators/:slug` URLs to persisted Translator/category metadata, and uses no AI. BigInt counters remain BigInt until bounded ratios are converted.

Pin signals and cluster opportunities are separate persisted concepts. A Pin-level winner requires 14 observed days, at least 1,000 impressions, 20 outbound clicks, and activity in three of four weeks; one Pin can therefore be reported even when its cluster is not durable. A winner cluster opportunity additionally requires at least two meaningful contributors (each at least 250 impressions, five outbound clicks, and two active weeks) and no more than 80% top-Pin outbound concentration. Inventory gaps require at least three Pins, two meaningful contributors, 30 outbound clicks, and no more than one destination.

Rising requires at least five recent observed days, prior evidence (or a stronger 1,000-impression/20-click launch from zero), 500 recent impressions, and 10 recent outbound clicks. Reach must grow at least 25%, outbound clicks at least 50%, or the stronger from-zero threshold must hold. CTR may not decline more than 30%, and save rate may not decline more than 50% when at least five previous saves exist, unless outbound growth is at least 75%. A rising cluster opportunity additionally requires two recent contributors with at least 200 impressions/five outbound clicks and no more than 80% concentration.

Fatigue requires at least five observed days in both seven-day periods, previous performance of at least 500 impressions/10 outbound clicks, reach decline of at least 40%, and outbound decline of at least 30%. CTR improvement of at least 20% makes the signal cautious. Strong fatigue additionally requires declining CTR of at least 10%, declining save rate of at least 20%, or outbound decline of at least 50%. Only strong fatigue with two previous contributors of at least 200 impressions/five outbound clicks becomes a cluster opportunity. Stale evidence suppresses rising/fatigue opportunities; missing recent days cannot create fatigue.

Without collected conversion evidence, scoring weights are demand 45%, content fit 25%, freshness 20%, and evidence confidence 10%. When conversion is collected, weights are demand 35%, conversion 20%, content fit 20%, freshness 15%, and evidence confidence 10%. Duplication, concentration, and partial/stale evidence-risk penalties are then subtracted and the result is clamped to 0–100. Missing conversion is removed from the weights rather than scored as zero. Cost is `NOT_APPLICABLE`. `TrendProvider` is optional and only `NullTrendProvider` is wired. Full inventory remains intentionally broader than the eligible subset analyzed here.

The daily key is `opportunity-intelligence:opportunity_intelligence_v2:YYYY-MM-DD`. Persistence and compact `GrowthActivity` are idempotent per UTC analysis date/model. Phase 7 is complete, production deployed, and live validated. Growth and attribution remain disabled. It adds no external call, Pinterest/Translator/Ideas mutation, publishing, creative generation, recurrence, cron, or persistent Growth worker. Phase 8 — Translator Autopilot — is next.


### Phase 7 clustering v2 correction

The initial production v1 run analyzed 221 eligible Pins but collapsed them into the structural route topic `translators`. V1 records remain unchanged. `content_clustering_v2` and `opportunity_intelligence_v2` allow a corrected same-day run under the existing date/model unique key and versioned job key; scoring remains `opportunity_scoring_v1`. Recognized Translator destinations never tokenize the raw path. Candidate trust order is specific primary category, resolved Translator slug/name/legacy category, safe translator-slug fallback, Pin title/description, then terminal-only content for unknown destinations.

Candidates require document frequency of at least two. In corpora of ten or more Pins, candidates appearing in more than 60% of documents are rejected. Remaining candidates sort by trusted source weight, lower document frequency, and lexical order. Structural and corpus-generic terms include translator/translation, SayTwist, Ideas, generated, Pin/Pinterest, text/texts, and style/styles; `style` is generic in this product corpus rather than a durable niche. Singleton groups are discarded. Strong fatigue suppresses amplify and rising recommendations for the same cluster/run while raw signals and independent inventory gaps remain.
